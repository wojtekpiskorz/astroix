# Upstream findings for the packaged Electron host proof

Checked 2026-08-31. This is a source note for the disposable packaged-host proof. It does not select a permanent packager.

## Local contract established first

- This checkout is `@wojciechpiskorz/astroix` 0.0.29. Its manifest has no Electron dependency. `electron-to-chromium` in `bun.lock` is transitive, not a host runtime.
- [Task: prove the packaged Electron host and process lifecycle](https://github.com/wojtekpiskorz/astroix/issues/201) asks for an unsigned macOS packaged proof. [Grilling: ratify the runtime, origin, and project-introspection architecture](https://github.com/wojtekpiskorz/astroix/issues/202#issuecomment-5482445770) fixes the boundary: Electron main owns native window, single-instance, lifecycle, and Electron security policy. The control plane owns exact handles for the disposable project-plane worker and managed Astro child.
- Electron is currently unpinned, so every Electron statement below must be checked again against the proof's exact package. At this check, Electron's GitHub latest release and npm `latest` are **44.1.0**, published 2026-08-31. [GitHub release](https://github.com/electron/electron/releases/tag/v44.1.0), [npm package](https://www.npmjs.com/package/electron).

## Documented Electron and Node facts

| Finding | Source | Local decision it informs |
| --- | --- | --- |
| `ELECTRON_RUN_AS_NODE` starts Electron as a normal Node.js process. It is supported for forked children and spawned children that set it, but ignored if the `runAsNode` fuse is disabled. Electron excludes five OpenSSL and FIPS flags in this mode because its Node crypto uses BoringSSL. | [Electron environment variables](https://www.electronjs.org/docs/latest/api/environment-variables), [Electron fuses](https://www.electronjs.org/docs/latest/tutorial/fuses) | The proof may launch the Astroix worker with Electron's own exact executable plus `ELECTRON_RUN_AS_NODE=1`. Assert the worker's mode and the fuse outcome. Do not treat it as an interchangeable system Node binary or assume every Node flag works. |
| `nodeIntegration` defaults to `false`; `contextIsolation` has been default since Electron 12; renderer sandboxing has been default since Electron 20. A sandboxed renderer loses its Node engine. Electron's security checklist says to enable isolation and sandboxing, keep `webSecurity`, avoid privileged renderer APIs, and use a current Electron. | [BrowserWindow web preferences](https://www.electronjs.org/docs/latest/api/browser-window), [sandboxing](https://www.electronjs.org/docs/latest/tutorial/sandbox), [security checklist](https://www.electronjs.org/docs/latest/tutorial/security) | Set all three explicitly for the proof: `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true`. Give same-origin project code no preload bridge or raw Electron IPC. |
| Electron auto-approves permission requests until an app installs a custom handler. Complete handling needs both `setPermissionRequestHandler` and `setPermissionCheckHandler`; subframe checks may have a null `webContents`, so origin must come from the supplied request fields. | [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security), [session permissions](https://www.electronjs.org/docs/latest/api/session) | Install both handlers on the window session before loading the app. Return `false` for every permission and record the origin and permission in the proof. This includes `fileSystem`, media, display capture, local-network, and unknown permissions. |
| `will-navigate` can cancel main-frame user or page navigation. It is not emitted for programmatic `loadURL` calls or same-document navigation. `will-frame-navigate` covers both the main frame and subframes. Electron recommends parsing URLs and allowlisting exact origins, not prefix matching. | [webContents navigation events](https://www.electronjs.org/docs/latest/api/web-contents), [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security) | Main must call `loadURL` only for the active `*.localhost` app origin. Deny all unexpected top-level navigation. For the canvas iframe, permit only its natural URL on the active project origin and deny other frame navigation. |
| `webContents.setWindowOpenHandler()` decides renderer-created windows in main. Returning `{ action: 'deny' }` cancels creation. The security guide recommends registering it and denying unexpected windows. | [window-open API](https://www.electronjs.org/docs/latest/api/window-open), [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security) | Register a blanket deny handler. The proof must show that `window.open` and a `_blank` link do not create a window. |
| `webContents` exposes `render-process-gone`, while `app` exposes `renderer-process-gone`; both carry crash details. `app` also exposes `child-process-gone`, but that event is for Electron child types such as Utility, GPU, and sandbox helper, and explicitly excludes renderer processes. | [webContents crash event](https://www.electronjs.org/docs/latest/api/web-contents), [app process-gone events](https://www.electronjs.org/docs/latest/api/app) | Log and surface Electron renderer and internal-child failures. Do **not** mistake `child-process-gone` for supervision of the Astroix worker or Astro dev server. The control plane must supervise its own retained Node child handles. |
| `app.quit()` emits `before-quit`, then `will-quit` if windows close. A renderer `beforeunload` may cancel the quit. `app.exit()` is immediate and omits those lifecycle events. | [Electron app lifecycle](https://www.electronjs.org/docs/latest/api/app) | Begin the idempotent `ProjectRun.stop()` path from `before-quit`; allow the normal quit only after the close report settles. Keep a separately observed forced path for timeout or fatal termination rather than assuming Electron events clean project children. |
| Finder launches on macOS are single-instance at the system level, but command-line launches bypass that mechanism. `requestSingleInstanceLock()` is required for CLI launches. If it returns `false`, the second instance should quit; the primary receives `second-instance` after `ready`. `argv` is not stable, so exact data belongs in `additionalData`; macOS/Linux messages above 32 MB are dropped. | [Electron `requestSingleInstanceLock`](https://www.electronjs.org/docs/latest/api/app) | Call for the lock at main startup, before booting the control plane. The second-launch proof must use the packaged executable from Terminal, confirm only one registry and fixed-port writer, and confirm the primary focuses or reports the second-launch request. Do not use raw argv as an authority channel. |
| `process.resourcesPath` is the packaged resources directory. Manual Electron packaging puts macOS app code at `Electron.app/Contents/Resources/app/`, or `app.asar` at `Electron.app/Contents/Resources/app.asar`. | [Electron `process.resourcesPath`](https://www.electronjs.org/docs/latest/api/process), [Electron application packaging](https://www.electronjs.org/docs/latest/tutorial/application-distribution) | Locate shipped worker entry and static assets from `process.resourcesPath`, not the current working directory or a developer checkout. The proof should record the resulting bundle paths. |
| `spawn(command, args, options)` takes an executable and argument array. `shell` defaults to `false`; enabling it with unsanitized input permits command injection. `cwd` and `env` are explicit, and a missing command or cwd yields `ENOENT`. | [Node child_process](https://nodejs.org/api/child_process.html) | Resolve a concrete executable first, pass a fixed argument vector, set `shell: false`, `cwd`, and a deliberately constructed environment. No command string and no interactive-shell `PATH` lookup. |

## Upstream source-code observation

[Electron's macOS entry point](https://github.com/electron/electron/blob/355f0fa1f0dc34a7ebf393dac05745e54e66f610/shell/app/electron_main_mac.cc) checks both the `runAsNode` fuse and the `ELECTRON_RUN_AS_NODE` environment variable, then calls the Node start path before Electron main. [Electron's own Node spec](https://github.com/electron/electron/blob/355f0fa1f0dc34a7ebf393dac05745e54e66f610/spec/node-spec.ts) has a test that spawns `process.execPath` with that variable and verifies no Electron `window` or process type is present.

This is implementation evidence from Electron's `main` at the linked commit, not a replacement for the documented API and not proof that a future Electron release keeps the same internal route. The proof should execute the packaged version it installs.

| Developer ID signing identifies software distributed outside the Mac App Store. Notarization is a distinct Apple scan that yields a ticket Gatekeeper can retrieve. Notarization requires a Developer ID certificate, Hardened Runtime, secure timestamp, and valid signatures. They are later distribution work. |
| macOS still allows a user to open an app from an unknown developer after an initial failed launch through Privacy & Security > Open Anyway. The latter is a manual tester procedure, not a distribution pass. |

## Inferences and proof charter

1. Spawn the Astroix control-plane worker with the packaged Electron executable, an absolute worker-entry path resolved from `process.resourcesPath`, `ELECTRON_RUN_AS_NODE=1`, `shell: false`, and explicit `cwd` and `env`. This tests the exact packaged runtime without inheriting the user's shell setup.

2. Resolve the managed project's Node and Astro command from the registered project's installation, validate it, then spawn that exact path with a fixed argv vector and `shell: false`. This follows the control-plane ownership ruling in [Grilling: ratify the runtime, origin, and project-introspection architecture](https://github.com/wojtekpiskorz/astroix/issues/202#issuecomment-5482445770) and Node's process contract. Electron does not provide project-command discovery for Astroix.

3. Keep Electron main thin. Its testable responsibility is the native policy above. Worker, managed dev server, timers, watchers, proxy, readiness, and recursive close report remain in the control and project planes. Electron's `child-process-gone` cannot replace Node child-handle supervision.

4. The proof's `BrowserWindow` policy should be observable, not only configured: assert preferences, denied navigation and popups, both denying permission handlers, no exposed preload API, second CLI launch behavior, renderer crash event, Electron child-process event if one can be induced safely, and normal versus forced close results.

5. A disposable arm64 app that opens locally proves packaged mechanics and lifecycle only. It does not prove public distribution, Developer ID identity, notarization, Gatekeeper acceptance, updater behavior, cross-architecture support, or a permanent Forge versus builder choice.

## Compatibility caveats

- The Electron documentation uses `latest`; lock the proof to its installed Electron version and record `process.versions.electron`, its fuses, macOS version, machine architecture, and the bundle's signed helper inventory.
- `ELECTRON_RUN_AS_NODE` has an intentional compatibility gap for crypto-related Node flags. If the worker needs those flags, reject that proof configuration rather than silently changing its semantics.
- Apple Silicon's ad-hoc rule is architecture-specific. Gatekeeper behavior also depends on quarantine provenance and the tester's machine policy, so capture it as an OS observation rather than a portable assertion.
