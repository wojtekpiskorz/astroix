# Standalone app pivot: Astroix manages local Astro projects

Status: accepted (2026-08-31, owner pivot · map #179, ratified #187) — **supersedes ADR-0001** (deleted; see "Supersedes ADR-0001" below)

## Context

Astroix shipped as a dev-only Astro integration: an npm package installed inside the host project, serving a builder chrome over a same-origin iframe canvas. On 2026-08-31 the owner pivoted the product: the builder becomes a **standalone application that manages local Astro projects**, and the npm integration exits the product entirely.

The pivot is evidence-backed, not preference. Research #180 (outside-seams matrix, astro@7.2.7/vite@8) proved the app-side capabilities without any in-project integration: 9/10 capability rows clean-outside, with `getViteConfig` composition as the enabling seam — the supervisor can own a vite server carrying astro's full plugin pipeline (content via fresh module runners, routes via `virtual:astro:routes`, zod introspection included), while the write loops and `src/core` never cared where they run. Spike #189 booted every load-bearing claim for real: `getViteConfig` boots supervisor-side from the project's own install (~800 ms, middlewareMode, no integration hooks via `configFile: false`), a plain reverse proxy with Host-based virtual hosting carries pages + the HMR websocket transparently (bytes verbatim, `vite-hmr` subprotocol), and Electron 44 resolves `*.localhost` to loopback. Transport research #181 settled the canvas origin strategy; runtime research #182 fed the Node ruling (#184).

## Decision

1. **Standalone app, zero-injection.** Astroix = supervisor + registry + per-project-vhost canvas + builder UI (the two verticals, Content and CSS, carry over). Hard invariants: **zero repo writes to registered projects** — the only files touched are the content/CSS files the user explicitly edits; astro.config and package.json of registered projects are never modified — and **no astroix dependency ever enters a registered project**. A hybrid (in-project dev-dep) returns only on a concrete capability gap proven in real usage; nothing is kept "just in case" (#183).
2. **Proxy transport.** One supervisor fixed-port origin serves the app UI from its bundle — the single UI code path for every shell. The canvas is a per-project vhost `<project>.localhost:<port>`: a reverse proxy (HTTP + ws upgrade) forwarding to that project's `astro dev --port 0` ephemeral port. Same-origin between UI and canvas is restored through the proxy, so the selector engine (`contentDocument`/`matches()`) ports unchanged. Binding implementation constraints from spike #189: never synthesize the `101` (forward upstream bytes verbatim); vite 8 answers ws upgrades only when `Sec-WebSocket-Protocol: vite-hmr` is carried. Per-port addressing is a documented fallback only (#181, #183).
3. **Node supervisor.** The supervisor is node-compat code with no bun-only APIs; Node is the shipped runtime. Pre-alpha distribution is **git-based** (distribution-ruling amendment, #188 charter resolution, superseding #184's original `npx`-from-public-npm vehicle): git clone or a release tag → `npm install` → run; **no npm publish** — `@wojciechpiskorz/astroix` stays reserved-dormant on npm, returning only as a config flip at a future public launch. Electron endgame: the supervisor hosted directly in Electron's main process — one runtime, no child-process/IPC layer. All testing is web-stack-first (supervisor origin in a browser); the Electron shell gets a minimal smoke pass only (#184). Delivery sequencing: Electron remains the assumed final deliverable but is **not a gate** — a full-coverage inner-testers pre-alpha ships as the plain web package; the Electron shell (macOS-first, unsigned, no notarization/auto-update) lands later over the same origin (#183, #184).
4. **Fresh-runner-per-request: hard doctrine.** Long-lived ModuleRunners serve stale content after data-store writes; fresh runners refresh in ~1 s (#189). Every supervisor-side content read runs in a fresh runner — this is a requirement, not an optimization (#183).
5. **npm toolchain.** The repo's package manager moves from bun to npm (evidence and migration plan in `docs/stack.md` decision 1, per research #190). The mechanical migration is an execution-charter lane (#188), not part of the ratification docs.
6. **Package identity.** The app inherits the package name `@wojciechpiskorz/astroix`, version line starting at **0.1.0**; the integration's published versions 0.0.1–0.0.29 are deprecated on npm (executed at ruling time, no legacy funnels — #185). Per the #188 distribution amendment the name stays **reserved-dormant** — the app package (`packages/app` in the charter sketch) carries it at 0.1.0 in its manifest, marked dormant/not published; the npm publish layer (publish workflow, NPM_TOKEN wiring, changeset PR rules) retires in charter lane #192. The registry lives at `~/.astroix/` (user-global JSON owned by the supervisor); the session model is single-active-session (#186).

## Supersedes ADR-0001

ADR-0001 ("Chrome delivery: prebuilt bundle for consumers, source-served only in our dev checkout") described hybrid delivery for a consumable integration package — the mechanism by which a *foreign host project* received the builder chrome. That consumer no longer exists: the UI belongs to the app, served from the supervisor's own origin (#183). Per the owner's ADR-hygiene ruling (invalidated ADRs may be marked outdated **or deleted outright** where they no longer describe anything real — #183, ratified as form-fork Q1(a) in #187), **ADR-0001's file is deleted**; its text is preserved in git history, and this ADR records the succession. Everything downstream of the hybrid delivery dies with it: the source-mode staging and its symlink mechanics (#150), the payload guard, the reload shield, the mode-discriminator lanes.

## Considered Options

- **Hybrid: keep the integration alongside the app** — rejected: research #180 proved zero-injection feasible on the current stack, and the owner's default is zero-injection; a hybrid survives only if real usage exposes a concrete capability gap. Nothing is kept "just in case" (#183).
- **Electron-first delivery** (ship the desktop shell before any web pre-alpha) — rejected: Electron is not a distribution gate; the web package on the supervisor origin reaches inner testers with zero installer/auth overhead, and the shell lands later over the same origin (#183, #184).
- **Bun as the supervisor runtime / repo toolchain** — rejected: Node is the shipped runtime (npx pre-alpha, Electron-main endgame — #184), and the toolchain evidence ruled npm over both bun (dead 1.3 line; 1.4 an 11-day-old total rewrite) and pnpm (12 = 5-day-old Rust rewrite; "not now" with a recorded fallback trigger) — #190.
- **Electron webview/WebContentsView for the canvas; `*.astroix` hostnames; /etc/hosts** — rejected in transport research #181 (async-only DOM access forcing an agent-protocol rewrite; `protocol.handle` cannot proxy ws upgrades; sudo and no wildcards respectively).

## Consequences

- The npm integration is retired: all published versions deprecated (executed 2026-08-31, #185); `src/node` (the integration source) is **not** carried as a monorepo member — its removal is sequenced by the execution charter #188. Current `main` keeps building until the restructure lands; nothing new ever ships from it.
- The repo evolves in place (no fresh repo); `src/core` (indexer, matcher, splice-writer, route resolution) survives intact.
- ADR-0002's module discipline survives and is restated for the app package in place (concrete monorepo paths finalized at charter #188, re-touch during #188 allowed); ADR-0003 (desktop-only viewport scope) stands unchanged — it aligns with the Electron endgame.
- e2e goes web-stack-first; `e2e/fixture` survives as the canonical test project; dogfood = the app against the fixture and real projects (#184, #185).
- AGENTS.md's header and commands reflect the app and the npm decision now; its Repo-layout paragraph is explicitly deferred to #188's charter.
- Fresh-runner-per-request, byte-verbatim proxying, and the `vite-hmr` subprotocol are binding constraints on the execution lanes (#183, #189).
