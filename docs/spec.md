# Astroix — Spec (v2, pivot)

Status: ready-for-agent · Pochodzenie: mapa wayfindera **#179** (pivot standalone-app; ratyfikacja właściciela 2026-08-31, kontrakt treści w #187) + rulings #183–#186 + research #180/#181/#182/#189/#190 + amendement dystrybucyjny czarteru #188 ("Distribution ruling amendment": pre-alpha git-based, bez publiku npm) · Zastępuje spec v1 (grilling 2026-08-26 + grilling stackowy 2026-08-26) **w miejscu** — tekst v1 żyje w historii gita · Nazwa produktu i aplikacji: **Astroix**; pakiet npm: `@wojciechpiskorz/astroix` (unscoped `astroix` zablokowany przez npm name-similarity rule vs `astro`); aplikacja dziedziczy nazwę po integracji i startuje od **0.1.0** (#185), na rejestrze **reserved-dormant** — bez publiku w pre-alpha (#188).

Astroix = **samodzielna aplikacja zarządzająca lokalnymi projektami Astro**: supervisor (Node) z registry projektów + builder UI z dwoma pionami (Content + CSS) nad kanwą na per-project vhost, oparta o repo-mapping stylów. Dwie twarde niezmienności (#183, ADR-0004): **zero zapisów do repo zarządzanych projektów** — jedyne dotykane pliki to te, które użytkownik jawnie edytuje (content/CSS) — oraz **żadna zależność astroix nigdy nie wchodzi do zarządzanego projektu** (astro.config i package.json projektów nietknięte). Filozofia hostów: **najnowsze Astro — narzędzie do robienia nowych projektów i ich maintenance, nie do utrzymywania legacy** (Astro ^7, Vite ^8, zod 4).

---

## Problem Statement

Agent wykonuje dziś ~90% pracy nad projektami Astro, ale ostatnie 10% — poprawka treści ("zmień lead w hero") i doszlifowanie stylów ("to zdjęcie ma być mniejsze i zaokrąglone") — zmusza użytkownika do ręcznego grzebania w codebasie, którego może w ogóle nie znać: szukania właściwego pliku markdown, frontmattera, pliku CSS odpowiadającego konkretnemu elementowi na stronie. To odwraca proporcje: trivialna zmiana kosztuje więcej niż cała agentowa budowa sekcji.

Problem ma dwie twarze:

1. **Content**: treść stron i postów żyje we frontmatterze Content Collections — edycja bez GUI to ręczne YAML-owanie i zgadywanie pól.
2. **CSS**: style elementów są rozsiane po plikach `.css` i scoped `<style>` w `.astro` — nie ma mapy "element na ekranie → plik w repo".

Odpowiedzią jest aplikacja stojąca **obok** projektów, nie pakiet w środku nich: Astroix zarządza lokalnymi projektami (registry, dev serwery, kanwa) i edytuje wyłącznie pliki, które użytkownik jawnie edytuje — projekt pozostaje czysty dla agenta, gita i produkcji.

## Solution

Astroix = standalone app (ADR-0004): **supervisor** na Node zajmuje jeden fixed-port origin, z którego serwuje UI aplikacji, i per-project vhosty `*.localhost` dla kanw; **registry** w `~/.astroix/` trzyma listę zarządzanych projektów. UI buildera ma dwa piony:

- **Content**: GUI nad Content Collections — formularze generowane automatycznie ze schem zod (custom fields = pola), body w edytorze markdown, auto-write (debounce ~300ms), walidacja inline nieblokująca zapisu.
- **CSS**: tryb zaznaczania na canwie. Klik w element → lista reguł z repo pasujących do niego, każda z plikiem i linią, z wskazaniem wygrywającej w kaskadzie → edycja inline (wiersze property→value z widgetami: kolor, jednostki, enumy; plus raw mode) → zapis text-splice do oryginalnego pliku źródłowego z auto-write debounce → HMR = live preview.

Kluczowa zasada: **repo-mapping, nie parallel world**. Builder czyta i pisze prawdziwe pliki repo tam, gdzie agent by je położył ("najbliższy dom"), więc repo pozostaje jednorodne, a agent pracuje obok bez świadomości istnienia aplikacji. Zero-injection jest twardym invariantem: aplikacja nigdy nie instaluje się w projekcie, nie modyfikuje jego configów i nie zostawia śladów poza jawnie edytowanymi plikami.

Synchronizacja dwukierunkowa (wymóg twardy): zapis w IDE → live update canvasu **i UI** (podświetlony element i preview jego reguł odświeżają się same po reindex); zmiana w builderze → zapis do pliku lokalnego. Selekcja elementu przeżywa reindex. Kanwę przeładowuje własny HMR zarządzanego dev servera; stan UI (registry, content-sync legs, reindex push) niesie WS supervisora (#183).

## User Stories

1. Jako developer (inner tester), chcę uruchomić Astroixa przez klon gita (albo tag release'u) → `npm install` → start, tak aby zacząć pracę bez instalowania czegokolwiek w jakimkolwiek projekcie. *(Zastąpione pivodem, #184/#185; dystrybucja przestawiona na git-based przez amendement #188 — pierwotnie w v1: instalacja pakietu w projekcie.)*
2. Jako developer, chcę dodać istniejący lokalny projekt Astro do aplikacji — wpisana ścieżka + walidacja supervisora (package.json + astro config, czytelny błąd przy odrzuceniu) — tak aby projekt nie wymagał żadnej instalacji ani zmian w repo. *(#186.)*
3. Jako developer, chcę utworzyć nowy projekt z poziomu aplikacji — nazwa + katalog nadrzędny + szablon → nieinteraktywny scaffold → automatyczna rejestracja — tak aby nowy projekt od razu żył w aplikacji. *(#186; dokładna mechanika scaffoldu = fog dla lane'u wykonawczego.)*
4. Jako developer, chcę odpalić i przeglądać projekt z poziomu aplikacji — dropdown projektów z dokładnie jedną aktywną sesją; przełączenie zatrzymuje poprzedni managed dev server i startuje nowy z prostym komunikatem ładowania; kanwa pod `projekt.localhost` — tak aby praca z projektem nie wymagała terminala ani znajomości portów. *(#186, #183.)*
5. Jako developer, chcę kanwę z prawdziwym viewportem (iframe), tak aby media queries i jednostki `vw` nie kłamały.
6. Jako developer, chcę tryb zaznaczania z hover outline, tak aby widzieć, co kliknę, zanim kliknę.
7. Jako developer, chcę móc wyłączyć tryb zaznaczania, tak aby normalnie klikać linki i interakcje na stronie.
8. Jako developer, chcę ostrzeżenie gdy selector elementu jest brittle (strukturalny), tak aby wiedzieć, że CSS może się oderwać po refactorze HTML.
9. Jako developer, chcę listę kolekcji i entry, tak aby znaleźć content do edycji bez znajomości ścieżek w repo.
10. Jako developer, chcę formularz generowany ze schemy zod, tak aby custom fields (np. `hero.title`, `hero.cta.href`) były polami, a nie YAML-em do odręcznej edycji.
11. Jako developer, chcę inline walidację zod przy polach, tak aby widzieć błąd przed zapisem.
12. Jako developer, chcę aby walidacja nie blokowała zapisu, tak aby móc zapisać draft łamiący schemę i zostawić poprawkę agentowi.
13. Jako developer, chcę edytor markdown z podglądem, tak aby poprawiać body bez otwierania IDE.
14. Jako developer, chcę auto-write dla contentu — debounce ~300ms po pauzie w pisaniu, podgląd żywy = kanwa przeładowywana przez sync Astro — tak aby treść pracowała jak style: natychmiastowa pętla edycja→dysk→podgląd, bez przycisku Save. *(Zmiana 2026-08-28, wayfinder #47 → #67: pierwotnie jawny Save; wygrała wspólna doktryna auto-write z pionu CSS — patrz Impl #14.)*
15. Jako developer, chcę tworzyć nowe entry jako draft (przez flagę we frontmatterze), tak aby szkicować posty z poziomu GUI.
16. Jako developer, po kliknięciu elementu chcę listę reguł CSS pasujących do niego — każda z plikiem i linią — tak aby wiedzieć, GDZIE w repo żyją jego style.
17. Jako developer, chcę wskazanie, która reguła wygrywa w kaskadzie, tak aby nie edytować przegranej reguły i dziwić się brakowi efektu.
18. Jako developer, chcę widzieć reguły ze scoped style w `.astro` (z odfiltrowanym hashem `data-astro-cid-*`), tak aby scoped style nie były czarną magią.
19. Jako developer, chcę badge `@media` przy regułach w media queries, tak aby wiedzieć, że reguła działa warunkowo.
20. Jako developer, chcę edytować regułę w miejscu przez widgety (kolor, jednostki, enumy), tak aby podstawowe poprawki nie wymagały pisania z ręki.
21. Jako developer, chcę raw mode, tak aby móc pisać dowolny CSS, łącznie z ręcznym `@media`.
22. Jako developer, chcę aby edycja zapisywała się do oryginalnego pliku źródłowego z zachowaniem formatowania, tak aby git diff był minimalny, a agent czytał znany sobie świat.
23. Jako developer, chcę auto-write z debounce i podgląd na żywo przez HMR, tak aby skręcanie stylów było natychmiastowe, bez przycisku Save.
24. Jako developer, chcę undo w pamięci sesji, tak aby eksperymenty były odwracalne bez angażowania gita.
25. Jako developer, chcę aby nowa reguła lądowała w pliku stylów najbliższego przodka elementu ("najbliższy dom"), tak aby repo pozostało jednorodne z konwentem agenta.
26. Jako developer, chcę dropdown wyboru miejsca zapisu nowej reguły, tak aby móc świadomie wybrać plik, gdy heurystyka nie trafia.
27. Jako developer, gdy element nie ma żadnego domu w repo, chcę fallback do per-route overrides ładowany na końcu kaskady, tak aby zawsze było gdzie pisać.
28. Jako developer pracujący równolegle z agentem, chcę mtime/hash guard przed zapisem, tak aby builder nie nadpisał pliku zmienionego pod spodem — zamiast tego przeładował i pokazał diff.
29. Jako agent, chcę czytać pliki pisane przez Astroixa jako zwykłe pliki repo, tak aby moja praca nie wymagała świadomości istnienia aplikacji.
30. Jako developer, chcę aby Astroix nigdy nie wykonywał operacji git, tak aby wersjonowanie było wyłącznie moją decyzją.
31. Jako developer, chcę aby UI aplikacji i kanwa były wzajemnie izolowane stylami — UI żyje na własnym originie supervisora, kanwa w iframe — tak aby style strony nie psuły UI i odwrotnie. *(Re-anchored pivodem: w v1 izolację dawał shadow DOM chroma w stronie hosta.)*
32. Jako developer, chcę pracować na localhost bez warstwy auth, tak aby narzędzie dev nie wymagało setupu bezpieczeństwa.
33. Jako developer, chcę aby zapis pliku w IDE odświeżał live zarówno canvas, jak i otwarty panel reguł wybranego elementu, tak aby builder i IDE nigdy się nie rozjechały.
34. Jako developer, po kliknięciu elementu chcę zobaczyć, z jakiego pliku komponentu pochodzi (atrybuty `data-astro-source-*` dodawane przez dev mode Astro), tak aby nawigacja "element → źródło" była natychmiastowa, bez grepowania po repo.

## Implementation Decisions

1. **Form factor: samodzielna aplikacja** (#183, ADR-0004). Supervisor + registry + builder UI (dwa piony) + kanwa na per-project vhost. **Delivery sequencing**: pre-alpha = czysty web-package dystrybuowany **z gita** — klon repo (albo tag release'u) → `npm install` → start na originie supervisora (bez dmg/installera); **bez publiku na npm** (amendement dystrybucyjny czarteru #188, po rulingu #184): pakiet `@wojciechpiskorz/astroix` zostaje **reserved-dormant** na rejestrze, a npm wraca dopiero jako config flip przy przyszłym publicznym launchu; aplikacyjny pakiet (`packages/app` w szkicu czarteru) niesie nazwę i wersję **0.1.0** w manifeście, jawnie oznaczone dormant/not published. Electron pozostaje założonym final deliverable, ale **nie jest bramką** pierwszej dystrybucji — pełnozakresowa pre-alpha dla inner testerów ściga się jako web-package, a shell Electrona dołoży się później na ten sam origin. **Electron endgame** = supervisor hostowany bezpośrednio w procesie main Electrona (jeden runtime, bez warstwy child-process/IPC). Stance v1 Electrona: macOS-first, unsigned (instrukcje bypassu Gatekeepera), bez notarization i auto-update; electron-builder vs forge — wybór na czarterze (#188). Repo ewoluuje w miejscu (bez świeżego repo); stara integracja npm wygaszona — wszystkie opublikowane wersje 0.0.1–0.0.29 deprecated na rejestrze w momencie rulingu, bez gałęzi maintenance i wyjątków na critical-fixy (#185); aplikacja dziedziczy nazwę pakietu, linia wersji od **0.1.0**, dist-tag `latest` przewraca się dopiero przy przyszłym publiku (pre-alpha bez publiku — #188).
2. **Twarde invariants: zero-injection** (#183). (a) **Zero zapisów do repo zarządzanego projektu** — astro.config i package.json nigdy nie są modyfikowane; jedyne pisane pliki to te, które użytkownik jawnie edytuje (content/CSS). (b) **Żadna zależność astroix nigdy nie wchodzi do zarządzanego projektu**. Hybryda (in-project dev-dep) wraca wyłącznie przy konkretnym capability gap wykazanym realnym użyciem; nic nie jest trzymane "na zapas".
3. **Supervisor na Node** (#184). Kod node-compat, zero API bun-only; Node = shipped runtime (bun nie jest targetem v1). CI compat harness na prawdziwych szwach supervisora — kompozycja `getViteConfig`, proxy + upgrade ws, fresh-runner — jako zwykła lane'a CI.
4. **Odczyt projektu: kompozycja `getViteConfig` + fresh-runner-per-request (twarda doktryna)** (#180, #189, #183). Supervisor składa własny serwer vite z pełnym pipeline'em pluginów Astro **z instalacji projektu** (resolve astro/vite przez `createRequire` z `package.json` projektu — zero version skew; `root` podany w obu miejscach; `command: 'serve'`; ~800 ms boot w middlewareMode). `configFile: false` w inline configu = szew bez integracji: config projektu się nie ładuje, hooki integracji nie wykonują się supervisor-side. Content przez `runner.import('astro:content')`; **fresh-runner-per-request to twardy wymóg, nie optymalizacja** — długowieczny runner serwuje stale content po zapisach do data store'u (świeży odświeża się ~1 s); `runner.close()` per sesji. Introspekcja zod przez `z.toJSONSchema(schema, { unrepresentable: 'any' })` (obsługuje `z.coerce.date()`). Route'y przez `virtual:astro:routes` (internals-coupled: wzorzec living w `routeData.route`).
5. **Transport: origin supervisora + per-project vhost** (#181, #189, #183). Jeden fixed-port origin supervisora serwuje UI aplikacji z bundla — **jedna ścieżka kodu UI dla każdego shella** (przeglądarka i przyszły Electron). Kanwa = iframe ładujący `<projekt>.localhost:<port>`: reverse proxy (HTTP + upgrade ws) → `astro dev --port 0` (efemeryczny port) tego projektu; same-origin UI↔kanwa przywrócone przez proxy, więc selector engine (`contentDocument`/`matches()`) portuje się bez zmian. Twarde reguły proxy (#189): **nigdy nie syntetyzować `101`** — forward bajtów odpowiedzi upstream verbatim (niosą `Sec-WebSocket-Accept`); vite 8 odpowiada na upgrade ws **tylko** z `Sec-WebSocket-Protocol: vite-hmr`. Kanały odświeżania: HMR dev servera przeładowuje kanwę; własny WS supervisora niesie stan UI (registry, content-sync legs, reindex push). Tryb per-port (Safari na macOS < 26) = udokumentowany fallback, nie budowany w v1; Electron 44 rozwiązuje `*.localhost` na loopback (multi-label, v4 i v6) — pełny production shape wyrenderowany w Electronie w spike'ie (#189).
6. **Registry: `~/.astroix/`** (#186). User-global JSON będący własnością supervisora — identyczny dla web-package i przyszłego Electrona (repo-local odrzucone przez zero-writes; appData odrzucone, bo pre-alpha nie ma Electrona). Tożsamość wpisu: **path = anchor**; display name mutowalny, default = nazwa katalogu; bez generowanych ID; przeniesiony projekt = nieprawidłowy wpis → re-add. Flowy v1: **add existing** = wpisana/wklejona ścieżka + walidacja supervisora (package.json + astro config) + czytelny błąd odrzucenia (folder picker przychodzi z shellem Electrona; web-run świadomie bez niego — dev wpisuje ścieżki); **remove** = skasowanie wpisu registry + stop managed dev servera, **nigdy** pliki projektu, z potwierdzeniem w UI; **create new** = nazwa + katalog nadrzędny + szablon → nieinteraktywny scaffold → auto-register (dokładne komendy/flagi scaffoldu = fog dla lane'u).
7. **Sesja: single-active-session** (#186). Dropdown projektów z dokładnie jednym aktywnym; przełączenie **zatrzymuje poprzedni managed dev server** i startuje nowy; v1 pokazuje podstawowy komunikat ładowania (bogatszy boot UX później). Zamknięcie aplikacji zabija wszystkie spawn procesy (orphan-free shutdown). Multi-server concurrency i multi-window — po pre-alpha (popyt testerów otwiera ponownie); multi-instance web-run dają już taby przeglądarki.
8. **Kanwa = iframe** (nie div-wrapper): prawdziwy viewport (media queries działają), izolacja stylów, tanie przyszłe zoom / resize / mobile preview przez transform i szerokość wrapper-a.
9. **Content v1**: wyłącznie Astro Content Collections (glob loader, schemy zod w content config). Odczyt supervisor-side przez fresh runner (Impl #4): `getCollection()` zwraca **sparsowane** `entry.data`/`body`/`filePath`; schemy przez introspekcję zod (wspólna instancja zoda z projektu). Formularz generowany z definicji schemy (zagnieżdżone obiekty → zagnieżdżone pola; `image()` → upload/picker). Zapis = pliki markdown z frontmatterem, serializacja przez Document API pakietu `yaml` (zachowuje komentarze, kolejność, styl cytowania). Źródła `.ts` data files i DB — poza v1. **Route resolution** (wayfinder #47, moduł #69): mostowanie URL↔entry w obie strony czystą heurystyką w `src/core` — wzorce route'ów (z manifestu `virtual:astro:routes`) × id entry; bez instrumentacji źródeł (`data-astro-source-*` jest stubem na astro@7.2.7 i sięga komponentów, nie entry). Selekcja wyłącznie jednoznacznego trafu: dokładnie jeden wzorzec jedno-parametrowy (segment lub catch-all — id glob-loaderów to ścieżki slugifikowane, więc `2024/post` pasuje do `[...slug]`) dopasowany do URL kanwy, wyłapany identyfikator istniejący w dokładnie jednej kolekcji; niejednoznaczność (ta sama nazwa w dwóch kolekcjach, nakładające się wzorce prowadzące do różnych entry, statyczna strona zasłaniająca dynamiczną) lub brak trafu — cisza, nigdy zły wybór. Nawigacja entry→kanwa korzysta z kandydackich route'ów i weryfikuje się forward-matchem po nawigacji (#71). **Active entry** (#71): wpis otwarty w edytorze treści. Wybór ręczny (klik na liście entries) otwiera formularz natychmiast, a nawigacja kanwy jest wtórna: odpala się tylko przy dokładnie jednym kandydackim route'cie i id niewspółdzielonym z inną kolekcją, po nawigacji weryfikuje forward-matchem, a nieudana weryfikacja zostawia wybór ręczny. *(Zmiana 2026-08-30, grilling content-UX: plurality wzorców prowadzących do tego samego wpisu nawiguje — wybór najbardziej konkretnego (segmentowy przed catch-all, potem najkrótszy); plurality do różnych wpisów pozostaje ciszą.)* Wybór reaktywny to route resolution z aktualnego URL kanwy przy każdym `load` same-origin iframe'a; działa cicho niezależnie od aktywnego taba, cisza rezolucji przy zwykłej nawigacji czyści wybór. Terminy glossary — **active entry**, **raw field** — opisują zachowania już rozstrzygnięte; **raw field** (#72): dowolny niewspierany węzeł schemy (unie, transformacje, rekordy, daty, literały…) renderowany jako wyraźnie oznaczone pole tekstowe z YAML tego poddrzewa — każda schema otwiera się w builderze, dziwne pola pozostają edytowalne, tylko bez widgetu, a `image()` to read-only metadane (`src`/`width`/`height`), których wartość round-trip'uje nietknięta. Reguły terminów żyją w `CONTEXT.md`.
10. **CSS indeks repo — hybryda**: statyczny skan źródeł projektu (`src/**`): globalne `.css` + bloki `<style>` z `.astro` (pozycje przez `extractStylesSync` z compiler-rs). Parser postcss (czysty CSS — bez SCSS, bez Tailwind emission). Indeks: selector → (plik, source range, media condition). To **prawda edycyjna** — dev mode nie generuje sourcemap CSS, a `is:inline` jest widoczne tylko w źródłach. Żywotność ("co realnie działa na podglądanym route'cie") i skompilowane formy scoped selectorów — z module graphu serwera supervisora.
11. **Matchowanie**: po kliknięciu, każdy selector z indeksu testowany na klikniętym elemencie przez `matches()` w kontekście dokumentu iframa; wyniki sortowane po specyficzności; wygrana reguła oznaczona; reguły w `@media` dostają badge warunku (warunek nie jest ewaluowany w v1). Selektory scoped (z hashem) rozpoznawane i prezentowane czytelnie.
12. **Edycja**: zmiany reguł to text-splice po source range z parsera — bez reprintu pliku, formatowanie i konwencje agenta nietknięte. UI reguły: wiersze property→value z inline-widgetami (color picker, stepper jednostek, dropdown enum) + toggle raw mode.
13. **Nowe reguły**: dom = plik zawierający style najbliższego przodka/rodzeństwa ("najbliższy dom"); dropdown z alternatywami jako escape hatch; fallback `src/styles/builder/[route].css` injectowany na końcu kaskady (wygrywa load orderem, bez `!important`). Nowych reguł nie piszemy do scoped bloków `.astro`; scoped style istniejące: czytane i edytowalne.
14. **Persistencja = auto-write w obu pionach** (doktryna urodzona w CSS, PR #36; content dołącza — zmiana 2026-08-28, wayfinder #47 → #67): zapis na pauzę w pisaniu (debounce ~300ms) do prawdziwego pliku w repo, bez przycisku Save. CSS: text-splice po source range, podgląd = HMR; undo = historia w pamięci sesji. Content: serializacja całego pliku (frontmatter przez Document API pakietu `yaml` + raw body), podgląd = sync Astro przeładowujący kanwę; hash guard (pkt 15) obowiązuje tak samo, okno utraty ≈ debounce. Zaakceptowane konsekwencje (#47, Q1.4): przejściowe stany złamane w trakcie pisania w wymaganym polu — ta sama klasa co edycja w IDE obok `astro dev`; plik contentu brudny na dysku w trakcie sesji edycji; git pozostaje jedynym "commitem" (US30 nietknięte). Walidacja inline nigdy nie blokuje zapisu (US11/US12) — draft łamiący schemę ląduje na dysku dla agenta, ~300ms po pauzie. Astroix nigdy nie wykonuje operacji git.
15. **Konflikt z agentem**: przed każdym zapisem weryfikacja mtime/hash pliku; przy zmianie pod spodem — przeładowanie i diff zamiast nadpisania.
16. **Izolacja UI przez architekturę transportu**: UI aplikacji renderuje się na własnym originie supervisora, kanwa w iframe — wzajemna izolacja stylów przez konstrukcję (w v1 integracji chrom żył w shadow DOM strony hosta; własny dokument UI czyni to zbędnym).
17. **Format stylów**: czysty CSS. W projektach z Tailwindem overrides po prostu ładują się po utility i wygrywają kaskadą — read-side będzie tam ubogi (spodziewane i OK).
18. **Sync dwukierunkny**: watcher (`server.watcher`) serwera supervisora jako jedyny subscriber FS → debounce reindex → push do UI przez **WS supervisora**; kanwę przeładowuje własny HMR zarządzanego dev servera (przez proxy). Świeżość contentu: obserwacja pliku data store (sygnał post-sync core); tablica route'ów: manifest `virtual:astro:routes` (odświeżany przy zmianach route'ów). Operacje UI→supervisor to zwykłe requesty (fetch). Selekcja elementu przeżywa reindex (re-match po zmianie plików).
19. **Instrumentacja źródeł = czytanie core Astro, nie własny transform**: w dev mode Astro dodaje do elementów atrybuty `data-astro-source-file` / `data-astro-source-loc` (mechanizm, na którym działa dev toolbar). v1 czyta je read-only — klik w element pokazuje plik/linię komponentu-źródła obok listy reguł. *(Uwaga T2, issue #3: na astro@7.2.7 + compiler-rs 0.4.0 `annotateSourceFile` jest stubem — atrybuty nie są emitowane; v1 potrzebuje mechanizmu własnego astroix lub zmiany strategii.)* Faza 2 ("nazwij ten element" → stabilne selectory) buduje na tym samym mechanizmie. Architektura (indeks + splicer) nie zmienia się przez to.

Stack, plumbing i narzędzia (React 19, Tailwind 4 + shadcn na Base UI, TanStack, **npm**, vitest, Playwright, Biome, changesets): **patrz `docs/stack.md`**. Pełna inwentaryzacja mechanizmów przejmowanych z core Astro/Vite (zamiast pisania własnych): **`docs/core-reuse.md`**.

## Testing Decisions

Dobra reguła: testujemy wyłącznie zachowanie zewnętrzne (wynikowe bajty plików, trafione reguły na fixture'ach), nigdy wewnętrzną strukturę indeksu.

**Unit**: doktryna bez zmian — czyste moduły `src/core` (indexer/matcher, splice-writer, route resolution) jako czyste funkcje nad fixture'ami; happy-dom, bez Astro.

**E2E: web-stack-first** (#184): wszystkie testy e2e żyją na originie supervisora w przeglądarce (`@playwright/test`); **shell Electrona, gdy powstanie, dostaje wyłącznie minimalny smoke** — nie własną macierz testową. `e2e/fixture` przeżywa jako kanoniczny projekt testowy (spike-proven przeciwko `getViteConfig`, #189/#185); dogfood = aplikacja contra fixture + realne projekty. Los istniejących lanek fixture (4311/4313/4314) i kształt lane'i CI — graduje na czarterze (#188).

Szwy (liczba celowo minimalna, czyste moduły + jeden e2e):

1. **Indexer/Matcher** (czysty moduł): wejście — źródła CSS/astro jako stringi; wyjście — indeks selector→(plik, range, media); oraz funkcja match(indeks, element) → posortowane reguły. Kluczowe casy: scoped hashe, `@media` badge, sort po specyficzności.
2. **Splice-writer** (czysty moduł): (treść pliku, range, replacement) → nowa treść. Testy: zachowanie formatowania, edycje na brzegach range'u, append reguły na końcu pliku bez nowej linii.
3. **E2E seam**: `e2e/fixture` (Astro 7, kolekcja ze schemą hero + co-located CSS) odpalany przez supervisor + Playwright na originie supervisora — pełna pętla: wybór projektu, klik elementu, edycja, asercja bajtów na dysku + reflect w iframe. Prawdę o selector engine mówi tylko prawdziwy Chrome (`[data-astro-cid-*]` — domyślna strategia `attribute`; `:where(...)` tylko po konfiguracji — weryfikacja T2, issue #3).

Wzorzec hybrydowy testów: `@playwright/test` w CI jako źródło prawdy; Playwright MCP lokalnie do interaktywnego debugowania i autoryzowania speców przez agenta (agent eksploruje przez MCP → pisze deterministyczny spec → CI go odpala).

- GitHub-connect web mode (user linkuje swoje GH, zdalne workspace'y) — odległa przyszłość, świeży wysiłek jeśli kiedykolwiek.

- Multi-server concurrency i multi-window — post-pre-alpha (#186).
- Astro < 7, Vite < 8, zod 3 (filozofia: nowe projekty, nie legacy); jakikolwiek ślad w buildach produkcyjnych projektów — wykluczony z definicji przez zero repo writes.
- WYSIWYG, edycja blokowa, drag-drop layoutu; SCSS; emission klas Tailwind; osobny panel wizualny Webflow-style.
- Widgety breakpointów (raw `@media` ręcznie tylko); UI kaskadowych przekreśleń DevTools-style.
- Resizable canvas, zoom, mobile preview (tanie później dzięki iframe, świadomie nie w v1).
- Element-naming przez instrumentację źródeł (faza 2).
- Content poza Content Collections (`.ts` data files, DB/CMS).
- Operacje git, auth (localhost dev only).
