# Research: avoiding double-React when the host project ships its own React

Ticket: [T3 · #4](https://github.com/wojtekpiskorz/astroix/issues/4) · Feeds ADR ticket [T4 · #5](https://github.com/wojtekpiskorz/astroix/issues/5) · Date: 2026-08-26
Method: primary sources only — Vite 8.2.2 source (read directly), vite.dev docs, React source + docs, and the source code of the comparable tools.

## Question

Astroix's chrome is a React 19 app served **as source** through the **host project's** Vite dev server via a virtual module (`docs/core-reuse.md` §1, `docs/stack.md` #10). React is a regular `dependency` of astroix (`react@^19.2.8` in `package.json`), not a peer. When the host project has its own React (possibly a different major, e.g. React 18 islands via `@astrojs/react`), both live in one Vite dev server. How do comparable tools avoid double-React, and what should astroix do?

## TL;DR

1. **Astroix's "double React" is cross-document, not cross-tree.** The chrome is a top-level document served by astroix middleware; the host page (with its React islands) lives in the `?builder=0` iframe (`docs/spec.md` decision 2). Each document is a separate JS realm with its own module registry, so the classic same-tree errors ("Invalid hook call") **cannot** occur between chrome code and host code — they never share a realm. The whole hazard is one level lower: **which copy does Vite resolve for the chrome's `react` imports**.
2. **Vite 8 keys optimized deps by bare specifier string, not by resolved path.** Whichever copy is registered first under `'react'` in the client environment's optimizer is served to *every* importer of the bare specifier — including the chrome. When the host ships React, the chrome silently gets the host's copy; `resolve.dedupe` can only ever point at the host-root copy; and a config-level `alias` for `react` is defeated by the same specifier-keyed lookup (verified in Vite source, §"Vite 8 mechanics").
3. **No surveyed comparable tool source-serves React through a foreign Vite module graph.** Every one of them prebuilds: prebuilt static iframe UIs (vue-devtools, Nuxt DevTools, vite-plugin-inspect, vitejs/devtools' own React example, Storybook's manager) or framework-free web components in the host page (Astro Dev Toolbar).
4. **Recommendation:** keep the chrome source-served for HMR (stack #10 stands), but make the chrome's React imports **never resolve through the host resolver**: publish-time prebundled ESM copies of `react`/`react-dom` shipped as astroix package assets, referenced through astroix-owned virtual ids (`astroix:react`). Fail loudly (dev-time check) if the chrome ever ends up on a foreign major.

## Astroix-specific facts that shape the answer

- Chrome entry: middleware returns HTML passed through `server.transformIndexHtml()` referencing `virtual:astroix/chrome` (`docs/core-reuse.md` §1). The chrome document loads `/@vite/client` (HMR works).
- Canvas: same-origin iframe loading the same URL with `?builder=0` — the untouched host page (`docs/spec.md` decision 2). Host React islands (if any) execute in the iframe's realm.
- `@vitejs/plugin-react` is added via `updateConfig`, `include`-scoped to chrome files "when the host doesn't use React" (`docs/core-reuse.md` §1) — implying two plugin-react instances when the host *does* use React (see Open questions).
- React is a `dependency` (not peer) of astroix: `react@^19.2.8`, `react-dom@^19.2.8`; peers are only `astro`/`vite` (repo `package.json`).
- The e2e fixture has no React, so none of the below is currently exercised by CI.

## Vite 8 mechanics (verified in source, v8.2.2)

These four facts decide everything. File references are `packages/vite/src/node/…` at tag [`v8.2.2`](https://github.com/vitejs/vite/tree/v8.2.2/packages/vite/src/node).

**M1 — Optimized deps are keyed by bare specifier, first registration wins.**
`vite:resolve-dev` calls `tryOptimizedResolve(depsOptimizer, id, …)` for every bare import before node resolution ([`plugins/resolve.ts` L470–480](https://github.com/vitejs/vite/blob/v8.2.2/packages/vite/src/node/plugins/resolve.ts)), and that lookup is `metadata.optimized[id] || metadata.discovered[id] || metadata.chunks[id]` — a map keyed by the **raw specifier string** ([`optimizer/index.ts` L1393](https://github.com/vitejs/vite/blob/v8.2.2/packages/vite/src/node/optimizer/index.ts)). Consequence: once the host's `react` is optimized, *every* `import … from 'react'` in the client environment — from any importer, including files inside `node_modules/@wojciechpiskorz/astroix` — resolves to the **host's pre-bundled chunk**. Node resolution from the chrome's directory (which *would* find astroix's nested `react@19`) is never reached.

**M2 — `resolve.dedupe` resolves from project root, always.**
`tryNodeResolve`: `if (dedupe.includes(pkgId)) { basedir = root }` ([`plugins/resolve.ts` L711](https://github.com/vitejs/vite/blob/v8.2.2/packages/vite/src/node/plugins/resolve.ts)). Docs: "force Vite to always resolve listed dependencies to the same copy **(from project root)**" ([vite.dev/config/shared-options.html#resolvededupe](https://vite.dev/config/shared-options.html#resolvededupe)). Dedupe can therefore only select the host-root copy — it cannot point astroix at its own nested copy.

**M3 — Imports from files inside node_modules skip optimization and are served raw.**
If the specifier is *not* already optimized, `tryNodeResolve` computes `skipOptimization = … || (importer && isInNodeModules(importer)) || …` and, when true, serves the dependency **as raw source** with only a `?v=` cache query ([`plugins/resolve.ts` L810–830](https://github.com/vitejs/vite/blob/v8.2.2/packages/vite/src/node/plugins/resolve.ts)). The CJS→ESM interop in `importAnalysis` only fires for **optimized** dep files (`depsOptimizer?.isOptimizedDepFile(resolvedId)`, [`plugins/importAnalysis.ts` L605–611](https://github.com/vitejs/vite/blob/v8.2.2/packages/vite/src/node/plugins/importAnalysis.ts)). React ships **CJS only** — no ESM condition in its `exports` map ([`packages/react/package.json`](https://github.com/facebook/react/blob/main/packages/react/package.json); long-standing ESM request: [facebook/react#11503](https://github.com/facebook/react/issues/11503)). So raw-serving an installed astroix chrome's `react` import means CJS in the browser: `require is not defined` / "does not provide an export named 'useState'". (Contrast: Vue ships real ESM, which is exactly why vue-devtools can get away with source-serving — see survey.)

**M4 — Config-level aliases for optimized specifiers are also defeated; and each environment has its own optimizer, but browser URLs only reach `client`.**
- `vite:pre-alias` runs *before* user aliases ([`plugins/index.ts` L65](https://github.com/vitejs/vite/blob/v8.2.2/packages/vite/src/node/plugins/index.ts)); for a bare id matching an alias pattern it first checks `tryOptimizedResolve` and returns the optimized chunk if present ("aliased dep already optimized", [`plugins/preAlias.ts` L40–55](https://github.com/vitejs/vite/blob/v8.2.2/packages/vite/src/node/plugins/preAlias.ts)). An alias `{ find: 'react', replacement: <astroix react> }` therefore **silently loses** whenever the host has `react` optimized.
- Every `DevEnvironment` gets its own `DepsOptimizer` (its own metadata/registry) unless disabled ([`server/environment.ts` L188–201](https://github.com/vitejs/vite/blob/v8.2.2/packages/vite/src/node/server/environment.ts)), and `resolve` is per-environment configurable ([vite.dev/guide/api-environment](https://vite.dev/guide/api-environment.html)). But the dev server's transform middleware hard-codes `const environment = server.environments.client` for all module requests ([`server/middlewares/transform.ts` L123](https://github.com/vitejs/vite/blob/v8.2.2/packages/vite/src/node/server/middlewares/transform.ts)) — there is no URL→environment routing for browser requests.

One more documented behavior for completeness: dependencies discovered only at request time trigger re-optimization and a **full page reload** ("Vite will re-run the dep bundling process and reload the page if needed", [vite.dev/guide/dep-pre-bundling](https://vite.dev/guide/dep-pre-bundling.html)).

## Options, with evidence and trade-offs

### 1. `resolve.dedupe`

Semantics (Vite 8): listed packages always resolve "to the same copy (from project root)" ([docs](https://vite.dev/config/shared-options.html#resolvededupe)); implementation sets the resolution base dir to root (M2). It exists to fix *accidental* duplication from hoisting/monorepo linking, where all importers mean the same app.

- **Helps when:** the goal is one shared copy at the host root and all consumers are version-compatible.
- **Silently fails / actively harms here:** for a plugin that *wants* its own copy, dedupe is a weapon pointed the wrong way. If the *host* sets `dedupe: ['react']` (their prerogative — common in React projects), the chrome's react is forced onto the host-root copy regardless of astroix's nested `react@19` (M1 makes this moot anyway once react is optimized; dedupe just makes it explicit). And astroix cannot use dedupe to select its own copy — root-based only. If the host root has *no* react, `dedupe: ['react']` resolves from root and finds whatever hoisting put there (with bun/npm, astroix's own `react` typically *is* the hoisted root copy; with pnpm's strict layout it isn't — dedupe then fails resolution or finds nothing).
- **Verdict:** not a tool astroix can use. Treat host-configured `dedupe: ['react']` as one more reason the chrome must not import bare `react` at all (see recommendation).

### 2. Aliasing the chrome's react to astroix's own copy

Two very different variants:

**a) Config-level `resolve.alias` (`react` → astroix's react path).** Silently defeated when the specifier is already optimized (M4, `preAlias` returns the optimized chunk before user aliases apply). A global alias would also hijack the *host's* react — the inverse catastrophe. Not viable.

**b) Per-import rewriting in astroix's own transform / virtual module** — chrome source never imports bare `react`; astroix rewrites (or authors) `react`-imports as astroix-owned ids (e.g. `astroix:react`) resolved by astroix's `resolveId` to a file inside the astroix package. This is structurally what vue-devtools does for its host-page overlay: `virtual:vue-devtools-path:overlay.js` → plugin's own dist path, file read by the plugin itself "to avoid getting shut out by vite's fs.allow check" ([`packages/vite/src/vite.ts` L155–168](https://github.com/vuejs/devtools/blob/main/packages/vite/src/vite.ts)). Because the id is not a bare specifier, M1/M2/M4 never engage: no optimizer hijack, no dedupe, no alias collision.
- **What breaks:** React is CJS-only (M3), so the resolved file cannot be raw `react/index.js` — the browser can't execute it and there is no interop for non-optimized files. The alias must point at an **ESM artifact** (see recommendation: publish-time prebundle). Also note two copies in one *page* are fine only because astroix's are in different documents (see "What actually breaks"); if astroix ever injected the chrome into the host document, two self-consistent copies would still render independently, but any component/hook/context crossing copies would fail.

### 3. `optimizeDeps` include/exclude interplay

- `include` exists to pre-bundle deps the scanner can't see and to force linked-package pre-bundling; `exclude` opts out of pre-bundling, with the documented caveat "CommonJS dependencies should not be excluded from optimization" ([vite.dev/config/dep-optimization-options](https://vite.dev/config/dep-optimization-options.html)). Runtime discovery of a missing dep causes re-bundling + page reload ([dep-pre-bundling guide](https://vite.dev/guide/dep-pre-bundling.html)).
- For a source-served UI in a foreign Vite, the scanner never sees the chrome's imports (the chrome HTML is synthesized by middleware, not an on-disk entry — the scanner crawls html entries from disk). So without action, first chrome load either (host has react) shares the host chunk silently, or (host has no react) hits M3 raw-CJS (installed package) or a discovery-reload cycle (linked/dogfood installs, where the chrome's realpath is outside node_modules).
- `include: ['react', 'react-dom']` from astroix's config hook does **not** select astroix's copy: include entries resolve from the project root (they are scanned with root as importer), landing on whatever is hoisted at root. It also *pollutes the shared registry*: registering `'react'` when the host has none would make astroix's copy **the** `react` for the host's future islands — a reverse hijack (M1). `exclude: ['react']` would break the host's own pre-bundling and forces raw CJS for everyone.
- **Verdict:** with bare `react` imports, `optimizeDeps` cannot express "astroix's copy for the chrome, host's copy for the host" — the registry is one-per-specifier per environment (M1, M4). Include is only useful as reload-churn mitigation for a *shared, compatible* copy. The virtual-id approach (option 2b) sidesteps the optimizer entirely.

### 4. Separate module graphs / environments (Vite 8 Environment API)

Each environment has an independent module graph and dep optimizer (verified: [`server/environment.ts` L188–201](https://github.com/vitejs/vite/blob/v8.2.2/packages/vite/src/node/server/environment.ts)), and `resolve` is per-environment configurable ([Environment API docs](https://vite.dev/guide/api-environment.html)). In principle astroix could create a `chrome` client-like environment with its own optimizer (registering *its* react under `'react'` cleanly, separate metadata) and its own alias — true isolation at the framework level.

- **Blocker:** browser requests are served from `server.environments.client` only — the transform middleware hard-codes it (M4). There is no documented mechanism for routing URLs to a custom environment. Astroix would have to serve the chrome's module requests from its own middleware via `environment.transformRequest(url)` and hand-wire HMR (`import.meta.hot` binding, `/@vite/client` injection is per-document, not per-environment). That is a research project of its own, undocumented territory — the Environment API docs frame custom environments around *runtime providers* fetching modules via module runners (SSR-side), not browser-served UIs.
- **Verdict:** viable in principle, disproportionate in practice — especially since astroix already has cross-*document* isolation for free (the iframe split). Revisit only if astroix ever moves the chrome into the host document or needs the chrome in the same graph as host modules.

### 5. What actually breaks with two React copies vs. what merely duplicates bytes

Error signatures (primary sources):

- **"Invalid hook call. Hooks can only be called inside of the body of a function component."** (React invariant 321). The official page lists three causes, including "You might have **more than one copy of React in the same app**", and prescribes `npm ls react`, deduplication/resolutions, and the `window.React1 === window.React2` probe ([legacy.reactjs.org/warnings/invalid-hook-call-warning](https://legacy.reactjs.org/warnings/invalid-hook-call-warning.html)). Mechanism: hooks resolve through module-scoped dispatcher internals (`ReactSharedInternals`) — a hook from copy A is a no-op-null during copy B's render. The same page notes the react-dom/app "same module" requirement: *the `react` import in app code and inside `react-dom` must resolve to the same module*.
- **Cross-copy elements half-work, then fail:** React tags element types with `Symbol.for('react.translucent.element')` etc. — the **global** symbol registry, deliberately cross-copy-safe ([`packages/shared/ReactSymbols.js`](https://github.com/facebook/react/blob/main/packages/shared/ReactSymbols.js)). So an element from copy B passed into copy A's tree passes the `$$typeof` check and only explodes later (missing hook dispatcher, contexts that never match). Symptom: confusing errors far from the cause.
- **Wrong-major-single-copy (the realistic astroix failure):** if the chrome is forced onto the host's React 18, nothing "duplicates" — the chrome just runs on 18. React 19-only APIs used by chrome code (`use`, Actions, `useOptimistic`, …) throw `TypeError: … is not a function`, and React Compiler output assumes its configured target — the compiler *can* target 17/18 but then requires `react-compiler-runtime` and `target` configuration, while React 19 is the zero-config default ([react.dev/reference/react-compiler/configuration](https://react.dev/reference/react-compiler/configuration)).
- **Raw-CJS serve (M3):** `require is not defined` or "The requested module … does not provide an export named 'X'".
- **What merely duplicates bytes:** two *self-consistent* copies, each rendering its own roots in the same page — this works; it's how micro-frontend pages run mixed versions (see the react-refresh/multi-app discussion [vitejs/vite-plugin-react#185](https://github.com/vitejs/vite-plugin-react/discussions/185) for the pattern and its refresh-preamble friction). Both copies register as separate renderers on the shared `__REACT_DEVTOOLS_GLOBAL_HOOK__`, so React DevTools still sees both trees. Cost: memory, devtools confusion, duplicate scheduler/refresh runtimes. **For astroix even this is moot: chrome and host are separate documents (separate realms), so the copies never coexist in one realm.**
- **Adjacent hazard — two `@vitejs/plugin-react` instances:** fast-refresh's preamble assumes one instance per page; known failure mode `@vitejs/plugin-react can't detect preamble. Something is wrong.` ([#151](https://github.com/vitejs/vite-plugin-react/issues/151), [#185](https://github.com/vitejs/vite-plugin-react/discussions/185)). Astroix's chrome document gets the preamble via `server.transformIndexHtml` — whether host-instance + astroix-instance double-injection into two different documents is clean needs a fixture (Open questions).

## How comparable tools actually do it

| Tool | UI framework | Delivery strategy | Double-React avoidance |
| --- | --- | --- | --- |
| **Astro Dev Toolbar** (core) | none — web components + per-app ShadowRoot ([app API reference](https://docs.astro.build/en/reference/dev-toolbar-app-reference/)) | framework-free code in host page | no framework to duplicate, by design |
| **Astro Dev Toolbar apps** with React/Vue/Svelte | author's choice | "Astro does not preprocess JSX code in dev toolbar apps, so **a build step is required**" — author prebuilds, framework copy travels inside the build ([recipe](https://docs.astro.build/en/recipes/making-toolbar-apps/)) | prebuild |
| **vite-plugin-vue-devtools** | Vue (panel), own copy | panel = prebuilt static assets `sirv(DIR_CLIENT, { single: true })` at `/__devtools__/` ([`vite.ts` L95](https://github.com/vuejs/devtools/blob/main/packages/vite/src/vite.ts)); host-page overlay = plugin's own dist via `virtual:vue-devtools-path:` + self-read bypassing `fs.allow` | heavy UI never enters host graph; overlay's `@vue/devtools-kit` keeps `vue` external (`neverBundle: ['vue']`, [`tsdown.config.ts`](https://github.com/vuejs/devtools/blob/main/packages/devtools-kit/tsdown.config.ts)) — tolerable because Vue ships ESM; React does not |
| **vite-plugin-inspect** | Vue (prebuilt) | `server.middlewares.use(base, sirv(DIR_CLIENT, { single: true }))` ([`src/node/index.ts` L117](https://github.com/antfu/vite-plugin-inspect/blob/main/src/node/index.ts)) | prebuilt static UI |
| **vitejs/devtools React example** (`plugin-file-explorer`) | **React** | UI has its **own Vite build** (`src/ui/vite.config.ts` → `dist/ui`), node side serves it statically: `context.views.hostStatic(uiBase, resolve(iframeDist))` + iframe view ([`src/node/plugin.ts` L27–41](https://github.com/vitejs/devtools/blob/main/examples/plugin-file-explorer/src/node/plugin.ts)) | prebuild React with the UI; iframe |
| **Nuxt DevTools** | Vue (prebuilt client) | iframe "devframe": "devframe's own static hosting: a local directory is served directly; the default remote source resolves per request from a locally installed `@nuxt/devtools-assets`, the on-disk cache, or its CDN" ([`packages/devtools/src/module-main.ts`](https://github.com/nuxt/devtools/blob/main/packages/devtools/src/module-main.ts)) | prebuilt static assets + iframe |
| **Storybook 8/9** | React (manager) | manager is Storybook's prebuilt app; user stories render in the preview **iframe** with the framework builder's own Vite config ([docs](https://storybook.js.org/docs/configure), [publishing](https://storybook.js.org/docs/sharing/publish-storybook)) | architecture-level split: prebuilt chrome + isolated preview doc |

**Survey conclusion:** the closest analogues — including an *official Vite-project React UI* (vitejs/devtools example) — all avoid the foreign-graph problem by **prebuilding the UI** and serving it as static assets (usually behind an iframe), or by not using a framework in the host page at all. None source-serves React through the host's module graph. Astroix's source-served chrome (for full HMR, stack #10) is the novel position; the survey shows the hazard zone it lives in.

## Recommendation (feeds the T4 ADR)

**Keep chrome source-served; stop importing bare `react`.** Concretely:

1. **Publish-time ESM prebundle of astroix's React.** One extra tsup/rolldown entry bundles `react` + `react-dom/client` (CJS→ESM, exactly what Vite's optimizer does for the host) into `dist/client/deps/react-esm.js`(name TBD) shipped in the npm package. Dev-only cost, version-pinned to astroix's own `react@19`.
2. **Virtual ids in chrome source:** chrome modules import `astroix:react` / `astroix:react-dom/client`; astroix's `resolveId` maps them to the prebundled file (plugin `load` reads it, or `/@fs/` path). Bare `react` never appears, so host `dedupe`, host aliases, optimizer specifier-keying (M1) and the node_modules raw-serve trap (M3) are all structurally out of reach. This is the same escape hatch vue-devtools uses for its host-page overlay.
3. **Never register `react` in the host optimizer from astroix** (no `optimizeDeps.include: ['react']`): one shared registry per specifier means astroix would become the host's react provider — a reverse hijack (M1).
4. **Dev-time guard in the chrome:** assert `React.version` starts with `19` (and that `react`/`react-dom` are the same module instance — the `window.React1 === window.React2` trick from the React docs, applied to `astroix:react` vs `astroix:react-dom`'s internals); on mismatch, render a loud dev overlay instead of a mystery crash. Catches future routing accidents.
5. **E2E fixture variant with host React** (React 18 island via `@astrojs/react` + one with React 19): locks the isolation claims into CI — today's fixture (no React) proves nothing about this hazard.
6. **Environment API (option 4): not now.** Per-environment isolation is real but browser-serving from a custom environment is unsupported by the dev middlewares (M4) — file as a revisit trigger, not a plan.

Trade-off accepted: the prebundled React chunk (~40 kB gzip dev-only) is not HMR-able — irrelevant, astroix never edits React. Fast Refresh still applies to chrome components (plugin-react transforms chrome files, preamble injected into the chrome document via `server.transformIndexHtml` — needs the fixture from step 5 to confirm two-instance coexistence).

## Open questions

1. **Two `@vitejs/plugin-react` instances, two documents, one server** (host islands + astroix chrome): preamble/fast-refresh interplay — known error signatures exist for single-document misuse ([#151](https://github.com/vitejs/vite-plugin-react/issues/151)); cross-document case needs the React-fixture e2e. If dirty: scope by `include` per instance (already planned in core-reuse §1) and verify the preamble lands once per document.
2. **Does `registerMissingImport` under a custom id (`'astroix:react'`) work** if we ever want the host optimizer to pre-bundle astroix's react instead of shipping a prebundle? Source suggests the registry keys by raw id, but chunk-naming/id validity for namespaced ids is unverified — only relevant as an alternative to recommendation step 1.
3. **Dogfood via `bun link` (symlink):** with `preserveSymlinks: false` (default) the chrome's realpath sits outside node_modules, flipping M3 into the runtime-discovery path — the virtual-id approach should make this moot; confirm on the linked fixture.
4. **Astro's own optimizeDeps contributions** (does Astro core or `@astrojs/react` pre-register `react` in `optimizeDeps.include` on all projects?) — affects *when* M1 engages, not the fix. Cheap to verify on the React fixture.
